# [Spike] フロントエンド技術選定調査（Streamlit継続 vs 他言語・他フレームワーク）

- 関連Issue: [#73](https://github.com/koji-s-private/llm-practice/issues/73)（本調査） / [#72](https://github.com/koji-s-private/llm-practice/issues/72)（プロトタイプ感の脱却、Streamlitのままカスタムテーマで対応済み） / #85（DocPilotへのブランディング刷新、#72対応PR）
- ステータス: 調査完了・提言のみ（本Issueでの実装・移行は行わない）

## 1. 調査の目的・背景

現在のフロントエンドは [Streamlit](https://streamlit.io/)（Python）で実装されている（`app.py`）。
UI/UX改善（プロトタイプ感の脱却、Issue #72）を継続的に進めるにあたり、オーナーから
「Python以外の言語をフロントエンドに導入すべきか、導入するならどの言語・技術が適切か」
という技術選定のSpike（調査）依頼があった。

本プロジェクトには以下の強い制約があり、この制約の中で実現性・コスト・メリットを整理する必要がある
（詳細は[AGENTS.md](../AGENTS.md)参照）。

- **無料制約**: 課金が発生する可能性がある操作は一切行えない（有料クラウドサービス・有料APIは不可）。
  ホスティングも含め、すべて無料枠・無料ツールのみで完結する必要がある。
- **自動運用前提**: 実装はAIチーム（coder/qa-engineer/reviewer、GitHub Actions上で動くClaude Code
  サブエージェント）による自動実装・自動テスト・自動レビューが前提。人間のオーナーは要件の投げ込みと
  PRの最終承認・マージのみを行う。
- **既存密結合**: バックエンドロジック（`ingest.py` / `rag_chain.py` / `memory.py`）はPythonで
  LangChain・Chroma・Ollamaと密結合しており、これらは全てローカルで無料動作する構成になっている。

本Issueは実際の移行実装ではなく、調査・比較検討の結果をまとめ、オーナーが移行の要否を
判断できる材料を提供することがゴールである。

## 2. 比較する選択肢

Issueの指定に従い、以下の3案を比較する。

1. **案A: Streamlit継続 + カスタムCSS/テーマの深掘り**（現状路線の延長）
2. **案B: Python製の別UIフレームワークへの乗り換え**（例: [NiceGUI](https://nicegui.io/)、[Reflex](https://reflex.dev/)）
3. **案C: TypeScript/JavaScript製フロントエンド + Python(FastAPI等)バックエンドAPI化**（例: React, Next.js, Svelte等）

## 3. 各選択肢の評価

### 3.1 比較表

| 観点 | 案A: Streamlit継続 | 案B: Python製別フレームワーク（NiceGUI/Reflex等） | 案C: TS/JS + FastAPI化 |
|---|---|---|---|
| **無料枠完結性** | ◎ 完全無料。追加の依存・ホスティング契約は一切不要（今と変わらず`streamlit run`のみ） | ◎ NiceGUI/Reflexともローカル実行は無料。ホスティングも自ローカル運用を続ける限り無料枠内 | ○ フロントエンドは静的ビルド + ローカルサーバでホスティング自体は無料枠内で完結可能（例: `npm run build`成果物をFastAPIから配信、または`vite dev`のローカル起動）。ただし依存パッケージ（npm）が増え、ビルド環境（Node.js）の追加導入が必要 |
| **統合・移行コスト** | ◎ ゼロ。既存の`app.py`をそのまま拡張するだけ | △ 中〜大。`rag_chain.py`のエージェント呼び出し・`memory.py`の会話保存・ファイルアップロードの再実装が必要。Pythonで完結する分、バックエンドの関数を直接呼べるのはStreamlitと同様（別プロセス化は必須ではない） | × 大。バックエンドをAPI化（FastAPI等でエンドポイント切り出し）する必要があり、`ingest.py`のファイル同期・`memory.py`のスレッド管理・ストリーミング応答など、`app.py`が担っている状態管理をHTTP境界を挟んで再設計する必要がある。認証・CORS等、Streamlitでは意識不要だった懸念も新たに発生する |
| **AIチーム自動実装のしやすさ** | ◎ 既存パターン（`st.chat_message`等）の延長でCoderが迷わず実装できる。テストも`tests/`の既存構成をそのまま踏襲可能 | ○ Pythonのままなので既存のqa-engineer/reviewerの知見・pytestの資産をほぼ流用できるが、新フレームワーク特有の書き方をAIが都度学習するコストがある | × 低い。フロントエンド（TS/JS）とバックエンド（Python）の2言語・2スタックを1つのAIチームで扱うことになり、レビュー観点・テスト戦略（Jest/Vitest等の追加）も二重化する。自動実装の失敗確率・レビュー漏れのリスクが最も高い |
| **UX自由度（#72への寄与）** | △ Streamlitの標準コンポーネント + カスタムCSSの範囲に限定される（レイアウトの自由度、リッチなアニメーション、複雑なインタラクションには限界がある） | ○ NiceGUIはQuasar（Vue）ベースでStreamlitより高度なUIコンポーネントを提供。ReflexはNext.js相当のコンポーネント表現力を持つ。Pythonのまま比較的高いUX自由度を得られる | ◎ 最も高い。React/Next.js/Svelte等は本来Web UI構築のためのエコシステムであり、デザインの自由度・パフォーマンス・エコシステム（UIライブラリ等）が最も充実している |
| **ローカル動作（Ollama前提維持）** | ◎ 影響なし。現状通りOllamaへの接続はバックエンド側で完結 | ◎ 影響なし。Pythonプロセス内で完結するため、Ollama接続方式は変更不要 | ○ 影響なし（バックエンドAPI経由でOllamaに接続する構成にできる）が、フロントエンド↔バックエンド間の通信（ストリーミング応答等）を新たに実装する必要があり、ローカル動作自体は維持できるものの構成要素が増える |
| **総合評価** | 最も低リスク・低コスト。UX自由度の天井が課題 | 中間案。UX自由度は上がるがPythonエコシステムとしては非主流で情報・実績が少ない | UX自由度は最大だが、移行コスト・自動実装リスクが本プロジェクトの制約と最も相性が悪い |

### 3.2 補足: 案Bの2フレームワークについて

- **NiceGUI**: [Quasar](https://quasar.dev/)（Vue.jsベースのUIキット）をPythonから操作する薄いラッパー。
  サーバーサイドでUIの状態を保持するモデルはStreamlitに近く、学習コストは比較的低い。MITライセンスで無料。
- **Reflex**（旧Pynecone）: Pythonのコードから内部的にReact + FastAPIのアプリを生成するフルスタックフレームワーク。
  表現力は高いが、内部でNode.js/Reactのビルドプロセスが動く（＝実質的に案Cに近い複雑さを一部内包する）ため、
  「Pythonだけで完結する」というメリットが薄れる場面がある。

### 3.3 補足: 案Cのホスティングについて

TS/JS化した場合でも、Vercel/Netlifyのような外部クラウドの無料枠にデプロイする必要は無く、
現状と同じくローカルPC上で完結させる構成（`npm run dev`または静的ビルドをFastAPIから配信）を
取れば無料制約は満たせる。ただし「ローカルでのみ動く個人開発ツール」という現状のスコープにおいて、
Web標準のフロントエンドスタックを持ち込む必然性（複数ユーザーへの公開、モバイルアプリ化など）は
現時点では存在しない。

## 4. 推奨案

**推奨: 案A（Streamlit継続 + カスタムCSS/テーマの深掘り）を維持する。**

### 理由

1. **本プロジェクトの制約と最も整合する**: 無料制約・AIチームによる自動実装という2つの制約下では、
   Python単一スタック・既存パターンの延長で完結する案Aが最も低リスクである。案Cはフロントエンド/
   バックエンドの2言語化により、AIチームの自動実装・自動テスト・自動レビューの複雑度と失敗リスクが
   大きく上がり、「自動運用が前提」という本プロジェクトの根幹と相性が悪い。
2. **移行コストに見合うだけの明確な必要性が現時点で無い**: 本プロジェクトは個人利用のローカルRAGツールであり、
   複数ユーザーへの同時公開・モバイル対応・高度なリアルタイムインタラクションといった、Streamlitの限界が
   直接的な障害になる要件は現状ない。
3. **Issue #72（プロトタイプ感の脱却）は既にPR #85でカスタムテーマ導入によって一定の成果を上げている**。
   `.streamlit/config.toml`でのテーマ設定、`app.py`でのタイトル・アイコン・キャッチコピーの調整など、
   Streamlitの範囲内でもUXは継続的に改善できる余地が残っている（例: レイアウト調整、`st.columns`を使った
   構成の工夫、追加のカスタムCSS注入など）。
4. **案B（NiceGUI/Reflex）はPythonのまま案Aよりやや高いUX自由度が得られるが、既存資産の書き換えコストに対して
   得られるメリットが不明瞭**。将来的にStreamlitの表現力が明確なボトルネックになった場合の次の選択肢として
   記録には残すが、現時点で乗り換える理由は無い。

### 推奨に至らなかった案の位置づけ

- 案B（NiceGUI/Reflex）: 「将来Streamlitの表現力に明確な限界を感じた場合」の次点候補として記録しておく。
- 案C（TS/JS + FastAPI化）: 「複数ユーザーへの公開」「モバイル対応」など、ローカル個人ツールという
  前提そのものが変わるタイミングでのみ再検討する。

## 5. 移行を検討する場合の次のステップ（本Issueのスコープ外）

本Issueの推奨案は「移行しない（Streamlit継続）」であるため、移行実装Issueは作成しない。

将来的にオーナーの方針転換（例: 複数ユーザーへの公開、モバイル対応の要望など）により
案B・案Cへの移行を検討する場合は、以下を別Issueとして切り出す方針とする（本Issueでは実施しない）。

- 案Bを採用する場合: NiceGUI/Reflexいずれかを選定した上で、`app.py`の機能（チャットUI・ファイル
  アップロード・会話管理サイドバー）を1機能ずつ移植する計画Issueを作成する。
- 案Cを採用する場合: まず`rag_chain.py`/`ingest.py`/`memory.py`をFastAPI経由で呼び出せるAPI層を
  切り出すIssueを先行させ、フロントエンド（TS/JS）の実装Issueをその後に続ける段階的な移行計画とする。
