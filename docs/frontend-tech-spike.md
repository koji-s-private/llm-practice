# [Spike] フロントエンド技術選定調査（Streamlit継続 vs 他言語・他フレームワーク）

- 関連Issue: [#73](https://github.com/koji-s-private/llm-practice/issues/73)（本調査） / [#72](https://github.com/koji-s-private/llm-practice/issues/72)（プロトタイプ感の脱却、Streamlitのままカスタムテーマで対応済み） / #85（DocPilotへのブランディング刷新、#72対応PR）
- ステータス: 調査完了。**2026-08-05、オーナー（koji）の明示的な指示により、当初の推奨（案A維持）から案C（TS/JS + FastAPI化）採用へ方針転換**（詳細は[4.1 方針転換の経緯](#41-方針転換の経緯2026-08-05)参照）

> **本ドキュメントの位置づけについて**: 3章の比較表は当初の調査時点（案A推奨時）の評価をそのまま残してある。
> 比較表の評価軸自体は依然として有効な検討材料だが、最終的な採否判断は4.1節に記載の追加要因（機能要件・
> オーナー自身のレビュー体制）を踏まえて行われている。

## 1. 調査の目的・背景

現在のフロントエンドは [Streamlit](https://streamlit.io/)（Python）で実装されている（`app.py`）。
UI/UX改善（プロトタイプ感の脱却、Issue #72）を継続的に進めるにあたり、オーナーから
「Python以外の言語をフロントエンドに導入すべきか、導入するならどの言語・技術が適切か」
という技術選定のSpike（調査）依頼があった。

本プロジェクトには以下の強い制約があり、この制約の中で実現性・コスト・メリットを整理する必要がある
（詳細は[AGENTS.md](../AGENTS.md)参照）。

- **無料制約**: 課金が発生する可能性がある操作は一切行えない（有料クラウドサービス・有料APIは不可）。
  ホスティングも含め、すべて無料枠・無料ツールのみで完結する必要がある。
- **自動運用前提**: 実装はAIチーム（coder/qa-engineer/reviewer、GitHub Actions上で動くClaude Code
  サブエージェント）による自動実装・自動テスト・自動レビューが前提。人間のオーナーは要件の投げ込みと
  PRの最終承認・マージのみを行う。
- **既存密結合**: バックエンドロジック（`ingest.py` / `rag_chain.py` / `memory.py`）はPythonで
  LangChain・Chroma・Ollamaと密結合しており、これらは全てローカルで無料動作する構成になっている。

本Issueは実際の移行実装ではなく、調査・比較検討の結果をまとめ、オーナーが移行の要否を
判断できる材料を提供することがゴールである。

## 2. 比較する選択肢

Issueの指定に従い、以下の3案を比較する。

1. **案A: Streamlit継続 + カスタムCSS/テーマの深掘り**（現状路線の延長）
2. **案B: Python製の別UIフレームワークへの乗り換え**（例: [NiceGUI](https://nicegui.io/)、[Reflex](https://reflex.dev/)）
3. **案C: TypeScript/JavaScript製フロントエンド + Python(FastAPI等)バックエンドAPI化**（例: React, Next.js, Svelte等）

## 3. 各選択肢の評価

### 3.1 比較表

| 観点 | 案A: Streamlit継続 | 案B: Python製別フレームワーク（NiceGUI/Reflex等） | 案C: TS/JS + FastAPI化 |
|---|---|---|---|
| **無料枠完結性** | ◎ 完全無料。追加の依存・ホスティング契約は一切不要（今と変わらず`streamlit run`のみ） | ◎ NiceGUI/Reflexともローカル実行は無料。ホスティングも自ローカル運用を続ける限り無料枠内 | ○ フロントエンドは静的ビルド + ローカルサーバでホスティング自体は無料枠内で完結可能（例: `npm run build`成果物をFastAPIから配信、または`vite dev`のローカル起動）。ただし依存パッケージ（npm）が増え、ビルド環境（Node.js）の追加導入が必要 |
| **統合・移行コスト** | ◎ ゼロ。既存の`app.py`をそのまま拡張するだけ | △ 中〜大。`rag_chain.py`のエージェント呼び出し・`memory.py`の会話保存・ファイルアップロードの再実装が必要。Pythonで完結する分、バックエンドの関数を直接呼べるのはStreamlitと同様（別プロセス化は必須ではない） | × 大。バックエンドをAPI化（FastAPI等でエンドポイント切り出し）する必要があり、`ingest.py`のファイル同期・`memory.py`のスレッド管理・ストリーミング応答など、`app.py`が担っている状態管理をHTTP境界を挟んで再設計する必要がある。認証・CORS等、Streamlitでは意識不要だった懸念も新たに発生する |
| **AIチーム自動実装のしやすさ** | ◎ 既存パターン（`st.chat_message`等）の延長でCoderが迷わず実装できる。テストも`tests/`の既存構成をそのまま踏襲可能 | ○ Pythonのままなので既存のqa-engineer/reviewerの知見・pytestの資産をほぼ流用できるが、新フレームワーク特有の書き方をAIが都度学習するコストがある | × 低い。フロントエンド（TS/JS）とバックエンド（Python）の2言語・2スタックを1つのAIチームで扱うことになり、レビュー観点・テスト戦略（Jest/Vitest等の追加）も二重化する。自動実装の失敗確率・レビュー漏れのリスクが最も高い |
| **UX自由度（#72への寄与）** | △ Streamlitの標準コンポーネント + カスタムCSSの範囲に限定される（レイアウトの自由度、リッチなアニメーション、複雑なインタラクションには限界がある） | ○ NiceGUIはQuasar（Vue）ベースでStreamlitより高度なUIコンポーネントを提供。ReflexはNext.js相当のコンポーネント表現力を持つ。Pythonのまま比較的高いUX自由度を得られる | ◎ 最も高い。React/Next.js/Svelte等は本来Web UI構築のためのエコシステムであり、デザインの自由度・パフォーマンス・エコシステム（UIライブラリ等）が最も充実している |
| **ローカル動作（Ollama前提維持）** | ◎ 影響なし。現状通りOllamaへの接続はバックエンド側で完結 | ◎ 影響なし。Pythonプロセス内で完結するため、Ollama接続方式は変更不要 | ○ 影響なし（バックエンドAPI経由でOllamaに接続する構成にできる）が、フロントエンド↔バックエンド間の通信（ストリーミング応答等）を新たに実装する必要があり、ローカル動作自体は維持できるものの構成要素が増える |
| **総合評価** | 最も低リスク・低コスト。UX自由度の天井が課題 | 中間案。UX自由度は上がるがPythonエコシステムとしては非主流で情報・実績が少ない | UX自由度は最大だが、移行コスト・自動実装リスクが本プロジェクトの制約と最も相性が悪い |

### 3.2 補足: 案Bの2フレームワークについて

- **NiceGUI**: [Quasar](https://quasar.dev/)（Vue.jsベースのUIキット）をPythonから操作する薄いラッパー。
  サーバーサイドでUIの状態を保持するモデルはStreamlitに近く、学習コストは比較的低い。MITライセンスで無料。
- **Reflex**（旧Pynecone）: Pythonのコードから内部的にReact + FastAPIのアプリを生成するフルスタックフレームワーク。
  表現力は高いが、内部でNode.js/Reactのビルドプロセスが動く（＝実質的に案Cに近い複雑さを一部内包する）ため、
  「Pythonだけで完結する」というメリットが薄れる場面がある。

### 3.3 補足: 案Cのホスティングについて

TS/JS化した場合でも、Vercel/Netlifyのような外部クラウドの無料枠にデプロイする必要は無く、
現状と同じくローカルPC上で完結させる構成（`npm run dev`または静的ビルドをFastAPIから配信）を
取れば無料制約は満たせる。ただし「ローカルでのみ動く個人開発ツール」という現状のスコープにおいて、
Web標準のフロントエンドスタックを持ち込む必然性（複数ユーザーへの公開、モバイルアプリ化など）は
現時点では存在しない。

## 4. 推奨案

**推奨（2026-08-05更新）: 案C（TypeScript/JavaScript製フロントエンド + Python(FastAPI)バックエンドAPI化）を採用する。**

当初（本ドキュメント初版時点）の推奨は案A（Streamlit継続）だったが、以下の理由により方針転換した。

### 4.1 方針転換の経緯（2026-08-05）

オーナー（koji）から、本Spikeの結果を踏まえて以下の明示的な指示があった。

- 複数ファイルの一括アップロードや、会話（チャット）の管理操作（一覧・切り替え・削除など）といった、
  ChatGPT等に近い操作性を今後実現したい。3.1の比較表で「UX自由度」が◎評価だった案Cを採用したい
- 3.1の比較表で案Cの最大の弱点とされていた「AIチーム自動実装のしやすさ」（フロントエンド/バックエンド
  2言語化によるレビュー・テストの複雑化リスク）について、オーナー自身がReact/TypeScriptの実務知見を
  持っており、AIチーム（特にreviewerサブエージェント）が生成したフロントエンドコードを人間側でも
  レビューできる。比較表の評価は「AIが実装する難易度」のみを見た評価であり、「オーナー自身がレビュー
  できるか」という軸は反映されていなかった
- 「無料で完結する」という制約は堅持した上での移行を希望する
- UI崩れが起きないことを強く重視する

この指示を受け、比較表の評価（3.1）自体は覆らないものの、比較表に含まれていなかった評価軸
（オーナー自身のレビュー体制、具体的な機能要件の顕在化）を踏まえて最終判断を案Cに変更する。

### 4.2 UI品質担保の方針（「UI崩れが起きないこと」への対応）

自動化されたプロセスで不具合の発生を数学的に0にすることは原理的に不可能なため、「絶対に」は目標として
掲げつつ、以下の複数の防御層でリスクを実務上ほぼゼロに近づける方針とする。

1. **型安全性**: TypeScript `strict`モードを必須にし、`tsc --noEmit`をqa-engineerのテスト工程に組み込む
2. **コンポーネント単体テスト**: Vitest + React Testing Libraryで主要コンポーネントの単体テストを必須化
3. **E2E・ビジュアルリグレッションテスト**: Playwright（ローカル実行・無料）でチャット送信・ファイル
   アップロード等の主要フローをE2Eテストし、スクリーンショット比較で意図しない見た目の崩れを検知する。
   ベースライン画像との差分が出た場合はreviewerが必ず目視確認するまでマージしない運用とする
4. **段階的移行**: 一気に全機能を切り替えず、Issue単位で機能ごとに移行し、都度オーナーが実機確認する
   （5章の移行計画を参照）。既存のStreamlit版（`app.py`）は移行完了が確認できるまで残し、
   問題があればロールバックできる状態を維持する
5. **オーナーによる最終レビュー**: reviewerサブエージェントによる自動レビューに加え、オーナー自身が
   React知見を活かして重要なUI変更をPRごとに確認する

### 4.3 案B・当初案Aの位置づけ

- 案A（Streamlit継続）: 無料制約・自動実装のしやすさの面では引き続き最もリスクが低い案として記録に残す。
  案Cの移行が難航した場合のフォールバック先として位置づける。
- 案B（NiceGUI/Reflex）: 今回は不採用。Pythonのまま案Aよりやや高いUX自由度を得られるが、案Cで
  直接得られるUX自由度・エコシステムの豊富さには及ばないため、今回のオーナーの要望には案Cの方が適合する。

## 5. 移行計画

案Cへの移行を、以下のIssueに分割して段階的に進める（1PR目安5ファイル以内というAGENTS.mdの方針に従い、
機能単位で分割する）。

1. **API層の切り出し**: `ingest.py` / `rag_chain.py` / `memory.py` をFastAPI経由で呼び出せるエンドポイントとして
   切り出す。既存のpytestベースのテスト資産をAPI層のテストとして移植・追加する。ストリーミング応答は
   FastAPIの`StreamingResponse`（Server-Sent Events）で実装し、外部の有料メッセージング基盤は使わない
2. **フロントエンド基盤構築**: Vite + React + TypeScriptの雛形を作成し、Vitest/Playwrightのテスト環境・
   ESLint/Prettierの静的解析環境を整備する
3. **チャットUI実装**: メッセージ送受信・ストリーミング表示・Markdown/コードブロック表示（`react-markdown`
   等）を実装する
4. **ファイル管理UI実装**: 複数ファイルの一括アップロード（`react-dropzone`等）、アップロード済みファイルの
   一覧・削除UIを実装する
5. **会話管理UI実装**: 会話の一覧・新規作成・削除・タイトル編集などの管理操作UIを実装する
6. **Streamlit版の廃止**: 案Cでの機能パリティが確認でき次第、`app.py`と関連ファイルを削除し、
   READMEの起動手順を更新する（移行完了後、独立したIssueとして実施）

### 5.1 採用ライブラリ方針（すべて無料・OSS、追加の有料契約なし）

| 用途 | ライブラリ | 備考 |
|---|---|---|
| ビルドツール | [Vite](https://vitejs.dev/) | 高速なローカル開発サーバ・ビルド。無料OSS |
| フロントエンド | [React](https://react.dev/) + TypeScript | オーナーの既存知見を活かせる |
| UIコンポーネント | [Tailwind CSS](https://tailwindcss.com/) + [shadcn/ui](https://ui.shadcn.com/) | shadcn/uiはコピー&ペースト方式でコンポーネントを取り込むため、npm依存が肥大化しにくい。Radix UIベースでアクセシビリティも担保 |
| データ取得・状態管理 | [TanStack Query](https://tanstack.com/query) | API通信のキャッシュ・再試行等を簡潔に扱える |
| 複数ファイル一括アップロード | [react-dropzone](https://react-dropzone.js.org/) | ドラッグ&ドロップ・複数選択に対応 |
| Markdown/コードブロック表示 | [react-markdown](https://github.com/remarkjs/react-markdown) + [react-syntax-highlighter](https://github.com/react-syntax-highlighter/react-syntax-highlighter) | 現行Streamlit版の`st.markdown`相当の表示を再現 |
| バックエンドAPI | [FastAPI](https://fastapi.tiangolo.com/) | 既存のPythonロジック（`ingest.py`等）をそのまま呼び出せる |
| コンポーネント単体テスト | [Vitest](https://vitest.dev/) + [React Testing Library](https://testing-library.com/react) | Jest互換でVite環境と親和性が高い |
| E2E・ビジュアルリグレッションテスト | [Playwright](https://playwright.dev/) | ローカル実行のみで完結し無料。スクリーンショット比較機能を利用 |

いずれもMIT等の無料ライセンスで、ホスティングも含め外部の有料クラウドサービスを新たに契約する必要はない
（フロントエンドのビルド成果物はFastAPIから配信するか、開発時は`vite dev`のローカルサーバをそのまま使う）。
